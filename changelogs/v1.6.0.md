## 🚀 New Features

### The project name comes from the directory when nobody has decided it
- A project with no `COMPOSE_PROJECT_NAME` in its properties is now known by its directory,
  using the same rule Docker Compose applies. **A project that has the property set is
  unaffected**, which is every project that went through `hm setup` until now.
- This closes a disagreement that was already there: with the property empty, Compose derived a
  name from the directory and the CLI still believed the name was the empty string. The `hm.*`
  labels were written empty, looking up a service's container found nothing, and `hm list` showed
  the environment under Compose's name rather than the CLI's.
- Two copies of the same repository in different directories are now two environments, which is
  what you want when you clone a project to look at a branch. A name recorded in the properties
  is still shared by every clone, because that is an explicit decision.
- From a worktree the name resolves to the main checkout, so a worktree still does not get an
  environment of its own.
- A directory that yields no usable name (`___`, only symbols) is refused with the project exit
  code and an explanation, instead of Compose's *project name must not be empty*.
- `hm setup` records the name **only when it differs from the directory's**. The question and its
  default are unchanged; what changes is what ends up written in a file that is committed and
  travels to every clone.
- Documented in `docs/project-name.md`.

### Named database copies: `hm db`
- **`hm db snapshot [--name=…]`** saves the database without stopping anything, **`hm db list`**
  shows what there is, **`hm db restore <name>`** goes back to one, **`hm db remove <name>`** deletes
  it.
- The copies live in `~/.hm/snapshots/<project>/`, outside the project: no `.gitignore` to touch,
  nothing that can end up in a commit, and **they survive `hm down -v`** — which is exactly when
  they are needed.
- Restoring empties the database first, so it returns exactly what was copied instead of a mixture
  with whatever was created afterwards. It asks you to type the project's name to confirm;
  `hm --yes db restore` skips that.
- Taken with `--single-transaction`, including routines, triggers and events, and compressed.
- **`hm db clear`** removes every snapshot of this project, **`hm db clear --all`** those of every
  project on the machine. Both list what they will delete and ask you to type the name of what is
  being destroyed, because these are the only copies.
- Verified on **every database image the tool can configure**, from MariaDB 10.2 to 12.3: the data,
  the routines and the triggers all come back, and nothing created after the snapshot survives it.
  The tools were renamed along the way (`mysqldump` → `mariadb-dump`, `mysql` → `mariadb`) and both
  names are resolved inside the container.

### The mail catcher is a choice: Mailhog or Mailpit
- Mailhog is unmaintained. Mailpit is its maintained successor, and it listens on the same ports
  —1025 for SMTP, 8025 for the interface— so Magento's configuration, the published ports and the
  address you have bookmarked are identical either way.
- New projects can be created with it: `hm setup --mail=mailpit`, or by answering the question
  `hm setup` now asks. Mailhog stays the default, so **no existing project changes**.
- An existing project switches when it wants to: set `MAIL_SERVICE` in its properties, then
  `hm setup -f` and `hm rebuild`.
- Whichever runs, it answers to the name `mailhog` on the Docker network, so a Magento that was
  installed pointing its SMTP server at that name keeps delivering without being reconfigured.
- `hm describe` reports the mailbox under `urls.mail`, and keeps `urls.mailhog` with the same
  value. `hm launch --mail` opens whichever the project uses; `--mailhog` still works.
- `hm doctor` checks that the configured catcher's image can be obtained, because
  `hiberusmagento/mailpit` is published to the registry manually: until that has happened,
  choosing Mailpit would otherwise fail halfway through `up`.
- Documented in `docs/mail.md`.

### An admin account you can use on day one
- The admin password is **generated** instead of being the same fixed string for the whole
  department, and it is shown once at the end of the install. It is never written to a file:
  `data/config.json` is shared by every project and records what you answer, so a password kept
  there became the next project's default and sat in plain text on disk. Setting one there
  explicitly is still respected.
- The install **registers the second factor** and draws its QR code in the terminal, so the admin
  panel is reachable immediately.
- The **key is shown as well as the code**, with the account it belongs to and the kind of factor
  it is: scanning is not always possible, and every authenticator offers to enter the key by hand.
  The `otpauth://` URI is there too, for pasting.
- The code is drawn by `endroid/qr-code`, which Magento already ships for the two-factor module's
  own admin screen — no new dependency on the host or in the image.
- A project that has the two-factor module disabled is told so and left alone: nothing is enabled
  behind your back.
- The install ends with one block carrying the storefront, the admin URL, the user and the
  password, instead of leaving them scattered up the scrollback.
- Documented in `docs/install.md`.

### `hm clean`: collect what dead projects left behind
- **`hm clean` shows what could be collected and deletes nothing.** That is the default behaviour,
  not a flag you have to remember. `--force` deletes, after listing everything and asking.
- Only environments this tool created **whose directory no longer exists** are collectable. A
  stopped project whose directory is still there is not rubbish, it is a stopped project — the
  distinction `docker system prune` cannot make.
- **Volumes that cannot be attributed are never deleted**, not even with `--force`. Volumes carry no
  `hm.*` labels, so one whose project has no containers left could belong to anything. They are
  listed by name for a person to judge.
- Database snapshots, images and build cache are never touched. What is not ours is reported, with
  the Docker command that clears it — and that command is not run for you.
- Documented in `docs/clean.md`.

### Destroying an environment now asks first
- **`hm down -v` asks before deleting the volumes**, names the ones it is about to delete, and
  offers to save a database snapshot first — the default answer. One letter separates it from
  `hm down`, which destroys nothing, and there was no warning between them.
- **`hm stop --snapshot`** saves the database before stopping. If the snapshot fails the
  environment is left running: stopped with no copy, after asking for one, is the worst outcome.
- **`hm docker-stop-all` asks too**, saying how many containers it will stop and how many do not
  belong to the current project. It reaches the whole machine, including other people's work.
- `hm down` without `-v`, and `hm stop` without options, are unchanged. So is everything without a
  terminal, or with `--yes`: somebody who automates `hm down -v` wrote it on purpose.
- Documented in `docs/down.md` and `docs/stop.md`.

## 🐛 Bug Fixes

### `hm setup` no longer discards a project's other properties
- Saving the project properties rebuilt the file from three keys, so any other property a project
  had —a custom `BIN_DIR`, for instance— disappeared on the next `hm setup`. The file is now
  merged instead of replaced.

## 🔄 Backward Compatibility

- No project changes name. Existing projects have the property set and are resolved exactly as
  before.
- `hm setup` no longer writes `COMPOSE_PROJECT_NAME` when the chosen name matches the directory.
  A script reading that key out of `properties.json` and expecting it to be present will find it
  absent; `hm describe --json` reports the resolved name and is the right source for it.
