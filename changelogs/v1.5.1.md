# Changelog v1.5.1 (2026-09-10)

One bug, and it made every domain this tool registers unreachable in Firefox.

## 🐛 Bug Fixes

### Domains registered by `hm` did not work in Firefox

- `console/commands/set-host.sh` wrote a single line per domain, `0.0.0.0 ::1 <domain>`. A hosts
  line carries **one** address and everything after it is an alias, so `::1` was read as an alias
  and the domain resolved to `0.0.0.0` only. `getent ahosts <domain>` never returned `::1`.
- Chrome and curl connect anyway, because the kernel sends a connection to `0.0.0.0` to the
  loopback interface, so the entry looked right everywhere except Firefox, which refuses the
  address outright. What Firefox reports is `CORS request did not succeed` with a `null` status,
  because that is how a failed cross-origin fetch is reported, and that is a very long way from
  `/etc/hosts`.
- The entry is now one line per address family:

  ```
  127.0.0.1 <domain>
  ::1 <domain>
  ```

- **An existing installation heals itself.** The malformed entry for the project domain is
  removed on the next `hm setup` or `hm set-host`, and nothing else in the file is touched:
  entries of other domains stay as they are, whatever shape they are in, and a domain that
  already resolves per family is left alone, password prompt included.

### `hm doctor` reported a domain as resolving when Firefox could not reach it

- `console/tasks/doctor/94-hosts.sh` looked for the name on a line, so the malformed entry passed
  the check and the diagnosis said `resolves locally` about a domain the browser refused.
- It now reports the `0.0.0.0` shape as a warning with the command that repairs it, which is how
  an installation nobody re-runs `set-host` on finds out that it has one.

### A project was believed to resolve because another one did

- The check was `grep -q "$DOMAIN" /etc/hosts`, an unanchored substring match: `shop.test` was
  considered registered because `myshop.test` was on the machine, and no entry was written for it.
- The name now has to be a name on the line, and its dots are dots, so `shop.test` is not matched
  by `shopxtest` either.

## 📚 Technical Improvements

### The decision and the rewrite left the command, so they can be tested

- Whether `/etc/hosts` has to be rewritten, and what it should contain, are now
  `hm_hosts_needs_repair` and `hm_hosts_repaired` in `console/helpers/hosts.sh`. They live apart
  from the command because everything around them needs the system password, and nothing that
  needs a password can be exercised by a test — which is how a malformed entry survived a release.
- `tests/unit/hosts_entries_test.sh` asks them what a hosts file can be in: a legacy entry for
  this domain, a domain already resolving per family, a domain missing, a legacy entry belonging
  to another domain, a file somebody already repaired by hand, and the two substring cases above.

### `/etc/hosts` is rewritten through a copy, never edited in place

- `sed -i` is not portable. BSD sed takes the argument after `-i` as the backup extension, so
  `sed -i -E` on macOS loses the extended regex, matches nothing, exits `0` in silence and leaves
  a root-owned `/etc/hosts-E` behind.
- A rename from a temporary directory would not carry the owner, the mode and, on macOS, the file
  flags this file has, so the new contents are copied over the original. It is also never written
  from an empty file: this is how the machine resolves every name it knows.

## 🔄 Backward Compatibility

- No interface changes. `hm set-host`, `hm setup` and their options behave as before.
- The container-side entries (`console/tasks/set_etc_hosts.sh`) already wrote one address per
  line and are untouched.
- Domains that were registered by hand are left exactly as they are. Only the
  `0.0.0.0 ::1 <domain>` line written by earlier versions of this tool, and only for the project's
  own domain, is removed.
