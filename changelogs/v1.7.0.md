# Changelog v1.7.0 (unreleased)

> Built on top of 1.6.0, which is in internal validation. Anything fixed there is brought forward
> into this version.

## 🚀 New Features

### A global proxy, so more than one project can be up at a time
- Every project publishes ports 80, 443, 3306, 9200, 8025, 5672 and 15672 on the machine, and there
  is only one port 80. **Two projects could not be up at once.** With the proxy they stop publishing
  anything and are told apart by their domain.
- **It is off by default and opt-in per project**: `"USE_PROXY": "true"` in the project's
  properties, then `hm setup -f` and `hm rebuild`. A project that does not turn it on behaves
  exactly as before, ports included.
- Auxiliary interfaces move to subdomains: `mail.project.local`, `queue.project.local`,
  `search.project.local`. Each gets a **wildcard certificate**, because one per domain does not
  cover them.
- **Hitch is dropped** from projects using the proxy. It existed to give Varnish the HTTPS it does
  not have, and the proxy terminates TLS now — which is also closer to production, where TLS ends
  at the balancer.
- `hm proxy up | down | status`. It starts on its own with `hm start` when the project uses it, and
  is not stopped when that project stops: others may depend on it.
- It needs ports 80 and 443, which a project *not* using it holds. That conflict is reported with
  the name of the environment in the way, instead of Docker's "port is already allocated".
- Requires **Docker Compose 2.24 or newer**, checked before generating anything: the overlay that
  removes a project's ports uses `!reset`, which arrived in that version.
- Documented in `docs/proxy.md`.

### `hm tunnel`: a way in to what cannot be routed by name
- MySQL and AMQP are not HTTP: they carry no hostname, and Traefik refuses to route them without
  TLS. `hm tunnel db` opens a temporary port to a service of the current project and tells you
  which one it got, so TablePlus and PhpStorm keep working.
- Runs in the foreground like `ssh -L`: the tunnel lasts as long as the command, and Ctrl-C removes
  what it started. `hm tunnel --close` clears anything a closed window left behind.
- The port inside the container is taken from the image when it declares one, and asked for when it
  declares several.
- Documented in `docs/tunnel.md`.

### `hm share`: a public address for showing work and catching webhooks
- **`hm share`** gives the project a temporary public address, through a Cloudflare quick tunnel:
  no account, no credentials, nothing installed on the machine. `hm share --stop` closes one left
  open.
- It asks first, and says what it is doing rather than "are you sure?": while it is open, anyone
  with the address reaches the environment, admin panel and data included.
- Runs in the foreground, so the tunnel lasts as long as the command and Ctrl-C ends it.
- Works with or without the proxy: the tunnel joins the project's network and reaches the web
  service by name.
- The address changes every time, and Magento's links still point at the local domain — irrelevant
  for webhooks, which is where this helps most. `docs/share.md` explains both.
- Cloudflared rather than ngrok, which has been blocked at the company before. Verified working
  from the company network before being built.

### No more password prompt for every project's domain
- `hm set-host` now **checks whether the domain already resolves to this machine** before writing
  to `/etc/hosts`. With a wildcard resolver for the TLD — one of ours or one already on the machine
  — there is nothing to write and nothing to ask for.
- `hm doctor` reports how a project's domain resolves: through `/etc/hosts`, through DNS, or not at
  all.
- **`.local` is unaffected and cannot be**: macOS routes it to mDNS, so a DNS server never sees
  those queries. Those projects keep working exactly as before, prompt included. This helps
  projects on another TLD, `.test` being the one reserved for it.
- No resolver is installed. Many machines already have one — Herd, DDEV, Valet — and fighting them
  for port 53 would break a working setup to save a prompt. `docs/dns.md` explains how to check and
  how to set one up if there is none.
- Nothing is ever removed from `/etc/hosts`.

### `hm verify`: one command that says whether the code holds up
- Runs the checks the project actually has — syntax, Magento coding standard, static analysis,
  formatting — and reports each one. **What is not installed is reported as skipped, never as a
  failure**: the tools differ in every project, and "no PHPStan here" and "PHPStan failed" lead to
  opposite actions.
- **Syntax is always checked**, because `php -l` needs nothing installed and catches what hurts
  most. A project with no tooling still gets something.
- Fast by default; `--all` adds unit tests and DI compilation, which take minutes. A command that
  takes five minutes does not get run after every change.
- `--changed` limits it to what differs from the base branch. Without one, everything is checked
  and the report says so.
- Exit code `0` only when nothing failed, so it chains as an agent's closing step or a CI stage.
  `--json` carries each check's status, count and raw output.
- It never fixes anything: a command that repairs what it finds makes changes nobody has read.
- Documented in `docs/verify.md`.

### `hm permissions`: what an agent may run, worked out rather than guessed
- Every command now declares what it does — `safe`, `caution` or `dangerous` — in the same file
  where it declares its description and group, which is the one you cannot skip when adding a
  command.
- **`hm permissions`** turns that into the permission configuration an agent needs: reading the
  environment and running Magento commands are allowed, destroying it asks first. `--strict` allows
  only what has no side effects at all.
- Two rules behind the classification: a command that wraps others is classified by its worst
  subcommand (`hm db` restores as well as snapshots), and a command that runs whatever it is given
  is dangerous however innocent its usual use — `hm exec`, `hm bash`, `hm mysql` and
  `hm docker-compose` can run anything, so allowing them is allowing everything.
- It prints and writes nothing: your settings file may have rules of your own.
- The tool already sorted commands in two hand-written lists — what a worktree refuses, and what
  needs full labels. Tests now assert all three agree, so a fourth consumer cannot appear quietly
  out of step.
- Documented in `docs/permissions.md`.

### `hm db freeze` / `hm db clone`: the same database, without the import
- A **template** is a byte copy of the data directory, frozen under a name. Standing an
  environment up from one costs the time of a file copy instead of the tens of minutes a server
  spends parsing a dump of data that already exists on the same disk.
- **`hm db freeze [--name=<name>]`** takes the copy, stopping the database while it does — a
  running InnoDB keeps pages in memory that are not in the files yet, and a copy taken underneath
  it is a crash to recover from rather than a copy.
- **`hm db clone [<project>/]<name>`** builds this project's data directory from a template. The
  qualified form is the point: the environment that needs a database is rarely the one that made
  it.
- It refuses while the environment is running, asks you to type the project name before replacing
  an existing database, and refuses a template made with a different database image — a 10.6 data
  directory under 10.2 starts, complains, and loses data in ways found much later.
- **`hm db templates`** lists them with their size and image; **`hm db drop`** deletes one.
- `hm clean` now sees them: a template belongs to no compose project, so the old rule could not
  attribute it, and they are the largest volumes the tool makes.
- Snapshots are unchanged and still the right thing for keeping a copy or handing it to somebody:
  portable, small, readable two server versions later. `docs/db.md` has the comparison.

### `hm worktree`: an environment per branch, next to the main one
- **`hm worktree add <branch>`** creates the git worktree, gives it its own compose project, its
  own subdomain, its dependencies and its database, and starts it. From then on `hm` commands run
  in that directory act on that environment.
- **Profiles** decide what runs: `lite` (php alone), `agent` (php, nginx, db, search and redis —
  the default) and `full`. A branch environment that also runs Varnish, TLS termination, a mail
  catcher and a queue costs more than the branch is worth. The profile is expressed by removing
  services from the configuration, so `describe`, `doctor` and the dashboard see the truth without
  knowing profiles exist.
- The registration lives in `~/.hm/worktrees/`, never in the checkout: `properties.json` is
  committed, and the worktree's project name written there would travel in somebody's commit.
- Dependencies are not installed again — linked to the main checkout on Linux, and the code volume
  copied on macOS, which is the same idea in the terms the platform allows. The database is cloned
  from a template.
- Reached at `https://<name>.<project domain>` through the global proxy, which is why the proxy is
  required: one set of ports per branch is the collision the proxy exists to end.
- **`hm worktree list`** and **`hm worktree remove`**, which refuses while there is uncommitted
  work: the environment can be rebuilt in seconds and the code cannot be rebuilt at all.
- The refusals of 1.6.0 are unchanged for a worktree with no environment of its own. That is still
  the case that repoints the main environment's mounts and destroys its database.
- Documented in `docs/worktree.md`.

### `hm mcp`: typed, read-only tools for agents
- **`hm mcp`** speaks the Model Context Protocol over stdin and stdout, offering five tools:
  `describe_project`, `list_environments`, `check_environment`, `service_logs` and
  `database_query`.
- Each wraps a command that already answers in JSON, so there is one implementation of "what is
  this project" and it is the one with tests. Nothing here can change the environment.
- **`database_query` is a SELECT, not a database connection**: comments are stripped first,
  because a comment is where a second statement hides; the statement must begin with `SELECT`,
  `SHOW`, `DESCRIBE` or `EXPLAIN`; and `INTO OUTFILE`, `INTO DUMPFILE` and `LOAD_FILE` are
  refused, because they read and write files on the host as the database user. Results are capped
  at 200 rows.
- A tool that cannot answer returns a result marked as an error, not a JSON-RPC error: a model can
  read the sentence, where most clients show a protocol error as a dead server.
- **`hm mcp --config`** prints the client entry and writes nothing.
- Documented in `docs/mcp.md`.

### Skills that teach commands that exist
- The skills describing this tool now live in this repository, in `skills/`: four of them, one per
  area of work — the environment, the database, debugging, and branch environments with the agent
  tooling.
- **They are checked by the suite.** Every `hm ...` in every skill must name a command that
  exists, with options declared for it in `command_descriptions.json` and services that are in the
  stack. It is a whitelist, and on its first run it found `hm down -v`: used everywhere, declared
  nowhere.
- The reason is on record: of the five skills published in `ai-tools`, the two most used taught
  `hm bash <command>` (about 150 times — `bash.sh` understands only `-r`, so the command is
  dropped and an interactive shell opens), `hm bash -c <service>` (never existed), and
  `hm mysql -e` (53 times, where the option is `-q`). Nothing checked them, so nothing said.
- `hm ai-pull` installs them from the installed copy of the tool rather than downloading them, so
  the skills a person has describe the version they are running. A skill you wrote yourself is
  still never overwritten without `--force`.
- `hm down` now declares `-v` in its command description, which is what the new test asked for.
- Documented in `docs/skills.md`.

### `hm ai-context`: write down what an agent otherwise invents
- **`hm ai-context`** writes the project's agent context: an `AGENTS.md` block with the resolved
  facts — versions, state, storefront and **the admin's real front name** — how to run commands,
  the exit-code contract, and what not to read or run.
- It regenerates only what is between its markers, so a hand-written `AGENTS.md` keeps everything
  around it. A `CLAUDE.md` that already exists is never touched; the line to add is printed
  instead. `.mcp.json` is merged, keeping any other servers.
- **No secrets are written.** The database is named, its password is not.
- **The exclusion list is declared once**, in `data/ai-exclusions.json`, with a reason per entry.
  It feeds the generated block, which explains, and `hm permissions`, which now emits `deny` rules
  and therefore refuses. Two mechanisms, one list.
- **`hm doctor` says when the context has gone stale**: the block records a fingerprint of the
  facts it was built from, so a context describing PHP 7.4 in a project that moved to 8.2 is a
  check that fails rather than an agent that is quietly wrong.
- Documented in `docs/ai-context.md`.

### `hm ai-doctor`: what is installed, where it came from, and whether it still is
- **`hm ai-doctor`** lists every skill and agent in the project with its origin and one of five
  states: `current`, `outdated`, `modified`, `custom` or `missing`.
- The state that pays for the feature is `modified`. `hm ai-pull` preserves custom skills by
  leaving alone what it did not install — so a skill somebody improved in place, without renaming
  it, was lost on the next pull without a word. Now it is said, along with the fix: rename it.
- **The checksum it recorded was never real.** It was computed with `sha256sum`, which macOS does
  not have and which cannot digest a directory in any case — and a skill is a directory. Every
  entry written on a Mac recorded an empty string that looked like a checksum. There is now a
  digest that works on both platforms, over a whole directory, with the file names in it.
- Provenance is recorded at install time: the repository, the branch or the tool version, and the
  date. For the bundled skills, `outdated` is therefore answered **offline**; for a downloaded
  repository the report says where and when and claims nothing about freshness, which is the
  honest consequence of following a branch rather than a version.
- It changes nothing: it is what you run before deciding whether `ai-pull --force` is safe.

### `hm mcp --write`: four bounded write tools
- **`hm mcp --write`** adds `cache_flush`, `cache_clean`, `reindex` and `config_set`. Without the
  flag they do not exist — absent from the tool list, not refused when called, because a tool that
  exists and says no is worse than no tool: the model sees it, plans around it, reads the refusal
  and reaches for a shell.
- **It is a smaller permission than what agents are given today.** An agent that has to flush a
  cache gets `hm magento`, which runs anything Magento can do, `setup:upgrade` included. Four typed
  tools replace that with four things and nothing else.
- **What is not offered, with or without the flag**: `setup:upgrade`, Composer, `di:compile`,
  database imports, removing an environment. Not slow versions of the tools above — the operations
  whose failure costs an afternoon.
- Every tool now declares the protocol's annotations, so a client can say "this one modifies your
  project" without knowing anything about Magento.
- `config_set` checks that the path looks like `section/group/field` before passing it on.
- `hm mcp --config --write` prints the entry with the flag in it.

### Anonymisation: recorded, expiring, and on by default where it matters
- **`hm worktree add --profile=agent` anonymises the cloned database by default.** With an agent
  this stops being good practice and becomes compliance: what an agent reads goes to a model, over
  a network, outside the company, and a development database is a copy of production.
  `--no-anonymise` opts out, because reproducing a bug that only happens with one customer's order
  history is a real thing people do.
- **A successful anonymisation is now recorded**, with its date, outside the checkout — and it
  **expires**. Restoring a snapshot, cloning a template, importing a dump or transferring a
  database clears it, because whatever those brought in has not been anonymised. A reassuring
  "yes" left over from before an import would be worse than no record at all.
- `hm describe` reports the state, `hm doctor` fails when an agent's environment holds data nobody
  anonymised, and the generated agent context says it in words: either the date, or *treat every
  row as real personal data*.
- **`hm masquerade` works without a terminal.** It passed `-t -i` to `docker run`
  unconditionally, so it had never once worked from CI, from a script or from an agent — the
  command that anonymises was usable only by a person at a keyboard, which is the opposite of what
  it is for.

### `hm clean` collects branch environments whose worktree is gone
- `hm worktree remove` is the tidy path and needs the directory to still be there. When somebody
  removes the worktree with git or deletes the folder, the containers and volumes were already
  collected — they carry `hm.root` — but the registration was left over for ever, showing as
  `missing` and refusing the name if that environment was ever wanted back.
- `hm clean` now lists those and collects them with `--force`, removing the containers and volumes
  **by name**: the directory that held the compose configuration is exactly what is missing.
- The branch is not touched, and neither are that project's snapshots.
- `hm worktree list` points at `hm clean` instead of reporting a state with no way out of it.

### Nothing silent for minutes any more
- **The rule is: something on screen before a hundred milliseconds**, for every operation that can
  take longer than a moment. The label is now printed by the same statement that begins the work,
  so it cannot arrive late.
- A spinner while silent work runs, with the **elapsed time** when it finishes: "done" says
  nothing, "done in 4m12s" tells you what to expect next time.
- **Nothing animates unless somebody is watching.** Not in a pipe, not in `--json`, not under
  `NO_COLOR`, not on a dumb terminal, not in a non-interactive run — those get the same
  information as two plain lines, with no escape sequence at all. `HM_NO_PROGRESS=1` turns it off
  on its own.
- Applied where the silences were: `db snapshot`, `db restore`, `db freeze`, `db clone`,
  `mysql -i`, the twenty-five seconds `hm clean` spends measuring volumes, and each check
  `hm verify` runs.
- Commands that already stream their own output are left alone: what they needed was a line
  first, not a spinner over the top of somebody else's output.
- Documented in `docs/progress.md`.

## 🔄 Backward Compatibility

- No project changes unless it opts in. The proxy is off by default and every port is published as
  before.
- Turning it on is reversible with the same two commands.
- A project using the proxy and one that does not cannot both be up: they compete for 80 and 443.
