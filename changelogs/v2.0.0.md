# Changelog v2.0.0 (unreleased)

> Everything 1.7.0 carries, 2.0.0 carries: the global proxy, `hm worktree`, `hm db`, `hm tunnel`
> and `hm share`, the multi-agent hardening. The two branches parted two commits short of 1.7.0's
> tip and each fixed those same two bugs on its own, so 1.7.0 was merged in to make the ancestry
> say what was already true. What is genuinely 2.0.0's own is everything below: the tool stops
> being a shell script.

## 🚀 New Features

### `hm web`: a dashboard, over the same calls as the CLI
- `hm web up | down | status` starts a small HTTP server and opens a browser dashboard that lists
  the environments on this machine, shows what each project is and what is wrong with it, and
  starts or stops it — the first thing built on top of the engine now that the engine is a
  library and not just a command line.
- It runs as its own session, the way `hm proxy` does, so closing the terminal does not take it
  down. `hm web up` returns only once the server actually answers.
- Every handler is one method on the same engine the CLI calls: `GET /api/environments` returns
  exactly the document `hm list --json` prints, and a test compares the two so a dashboard
  reimplementation of "what is running" can never quietly say something different.
- Two rules stand in front of it instead of a framework: it listens on loopback only, and every
  request needs the token printed in the link. The `Host` header is checked too, because a public
  DNS name can point at `127.0.0.1` and a page served from it would otherwise be same-origin with
  a server on this machine. No accounts, no sessions, no TLS — there is one user, whoever is at
  the machine.
- The page is one embedded HTML file with no build step, so a release that ships four binaries
  built with nothing but Go stays that way.
- It was named `hm serve` for one release cycle and renamed to `hm web` — beside the existing
  `hm tui` — before shipping, to avoid two commands (`hm tui`'s own "el panel" and a new
  "dashboard") reaching for the same word for two different screens.

## 📚 Technical Improvements — hm stops being a shell script

2.0.0 is a migration, not a rewrite of behaviour: `cmd/hm` is now a real Go binary, and the shell
implementation (`bin/run`, `console/`) stays as a bridge for whatever has not moved yet. The
measure of success is that the day-to-day experience does not change — same output, same
prompts, same exit codes, same `--json` — while the parts underneath do.

### The binary and the bridge
- The entry point is `cmd/hm`. A command already ported answers straight from Go; anything not
  yet ported is passed through, untouched, to `bin/run`. Nothing is ported by rewriting from
  memory — a port is checked by running both implementations on the same input and diffing the
  answer, which is how several of the bugs below were found rather than introduced.
- The code is split in two: `dockergento/` is the tool as a library — domain (`core`), ports,
  use cases (`app`) and adapters — and it is public only because Go's own `internal/` rule would
  otherwise stop a second consumer (the web server, later MCP) from importing it. `internal/cli/`
  is the terminal and nothing else: arguments, text or JSON, colour, exit codes.
- A release now installs a binary, not just a checkout: `goreleaser` publishes darwin/linux,
  amd64/arm64 builds, `hm switch`/`hm update` fetch the one matching the version they move to, and
  the installer falls back to the shell implementation when it cannot download one — a machine
  with no route to GitHub is left with a working tool instead of none.
- Talking to the Docker daemon goes through its own API and the Compose configuration is read with
  `compose-go` (the library Compose itself uses to merge, interpolate and validate) instead of
  shelling out to `docker` and `docker compose config` for every question. *Running* Compose stays
  with the `docker compose`/`compose-go` decision recorded as ADR-009 and its revision ADR-009 bis
  in `docs/research/2.0-arquitectura.md`: embedding the engine costs an 84 MB dependency graph
  against 10, and reimplementing the labels and configuration hash that decide whether a container
  belongs to a project is not a discount worth the risk of the two implementations recreating each
  other's containers.

### 32 of 65 commands answer from Go
Grouped the way the migration itself batches them — everyday commands first, then the ones that
touch state, then the rest:

- **Read and run, day to day**: `list`, `describe`, `doctor`, `start`, `stop`, `restart`, `logs`,
  `exec`, `magento`, `composer`, `bash`, `web`.
- **State**: `clean`, `down`, `setup`, `worktree` in full. `db` and `proxy` are ported **only
  halfway** and the router still routes them to shell for that reason — `db`'s templates
  (`freeze`, `templates`, `clone`, `drop`, which `worktree` is built on) and its snapshots
  (`snapshot`, `list`, `restore`, `remove`, `clear`, which `down -v` is built on) are both Go, but
  the command's own dispatch and usage text are not; the global proxy's Go implementation is what
  `start`/`post-start` call to bring it up, but `hm proxy` typed on its own still reaches shell.
- **The rest**: `mysql` and the whole `mysql -i` import sequence, `mysqldump`, the container
  wrappers (`purge`, `npm`, `n98-magerun`, `test-unit`, `test-integration`, `varnish-on`,
  `varnish-off`), `masquerade`, `copy-to-container`/`copy-from-container`, `set-host`, `version`.
- **`docker-stop-all` and `docker-compose` were the last two commands `hm start -s` still went
  back to shell for**, so they close this batch: `start -s` ran the Go orchestration and then
  handed the "stop everything else first?" question to `bin/run docker-stop-all`. One engine call
  now answers both, so the question, the counts and the refusal from a worktree exist once.
  `docker-compose <subcommand>` runs any Compose subcommand this tool does not wrap itself,
  against exactly the compose files the current project resolves to (base, platform overlay,
  worktree or proxy overlay), and refuses with an explanation rather than a confusing failure when
  Compose is not installed.
- Composer's `install`/`update`/`require`/`remove` on **macOS** stay in shell on purpose: there
  they are a copy-in, run, copy-back-and-overwrite sequence around `copy-to-container`, and
  porting only the four lines that call it would split one operation across two implementations.
  Everywhere else, and on Linux always, `composer` and `magento` run through Go.
- Nothing changed in `install`, `launch`, `rebuild`, or the AI-tooling and cloud commands — they
  are later batches, still entirely shell, and MCP (`hm mcp`) is untouched in this release: it
  is planned for the next phase (§6 of `MIGRATION.md`), not delivered here.

### The SQLite state registry
- What this machine knows about its projects and worktrees moved from a directory of small JSON
  files locked with `mkdir` to a SQLite database with two operations that were always going to
  need it: **handing out a worktree's database slot atomically** (two agents registering a
  worktree at the same moment can no longer both read "the lowest free number" and take it — the
  old race's symptom was two branches sharing a database) and **removing a worktree together with
  its allocation**, in one transaction instead of two writes that can be interrupted between them.
- Both topologies (classic and worktree) were modelled from day one, so a machine that never
  creates a worktree keeps an empty allocations table rather than needing a migration the day it
  does.
- What the registry does **not** hold is what is actually running — that is still asked of
  Docker every time, because a registry that goes on claiming an environment exists after someone
  removed it by hand would be worse than the files it replaces.
- The switch happened in one commit once `worktree add`, `list` and `remove` were all Go, because
  a half-ported registry — one implementation writing SQLite, the other still writing JSON — has
  no good outcome: a worktree the other side cannot see, or a removal the other side still thinks
  exists. `console/commands/worktree.sh` is now a 25-line delegator to the binary (it was 537).
  What earlier versions wrote to the old files is drained on the way in rather than abandoned, so
  upgrading does not lose worktrees already registered.
- Published binary size: 60.6 MB before the registry, 64.5 MB after (pure Go, no cgo, so the Linux
  build stays cgo-off).

### Proven without Docker: the CLI's test seam
- A ported command's behaviour is tested against a `newEngine` factory swapped for a fake that
  records what it was asked — no daemon, no network, no real project on disk. That is what makes
  it possible to test flag parsing, refusals and the shape of a question before the code that
  talks to Docker exists at all.
- The Go test suite (`go test ./...`, plus `test/e2e` for the built binary run the way a person
  runs it) now runs in seconds where the bash integration suite it is steadily replacing took
  twenty to twenty-five minutes; `tests/run.sh` runs and reports both, so a test moving from one
  suite to the other never reads as coverage disappearing. Several bash integration files for
  ported commands (`go_hosts_test.sh`, `go_transfer_test.sh`, `go_worktrees_test.sh`) are gone,
  their behaviour proven in Go instead.
- The rule that keeps the two suites honest: a command is ported, its Go test lands, *then* the
  shell implementation and its bash test are deleted — never the other way round — and a
  dedicated test (`tests/unit/migration_status_test.sh`) checks that `MIGRATION.md`'s table itself
  is not lying in either direction.
- What this buys in reliability: two regressions the porting work itself introduced — the
  worktree guardrail that refuses `start`/`stop`/`restart`/`down` from a worktree with no
  environment of its own, and the tool's own `hm.*` container labels being written empty — were
  both caught by this comparison discipline before shipping, not after (see Bug Fixes).

### Faster, measured on the same machine, same output byte for byte
| | bash | go |
|---|---|---|
| `list --json` | 205 ms | **63 ms** |
| `describe --json` | 285 ms | **94 ms** |
| `doctor --json` | 260 ms | **85 ms** |
| `start` (create the environment) | 555 ms | **265 ms** |
| `start` (environment already up) | 320 ms | **95 ms** |
| `stop` (stop the environment) | 10.3 s | 10.2 s — the container is what takes the time |
| `magento <anything>` | 210 ms | **75 ms** of wrapper |

Where it comes from: independent questions — a project's git branch, its Compose configuration,
its running containers — are asked at once instead of one after another, which a shell script
cannot do; and reading Compose configuration through `compose-go` is 1.7 ms against 58 ms for
`docker compose config` piped through a parser.

## 🐛 Bug Fixes

### `hm mysql -i` could leave a project without its own name
- Importing a dump into a project with no domain configured appended the domain to the *old*
  properties format's file, and every invocation of the tool converted that file into
  `properties.json` by overwriting it rather than merging. The result: `properties.json` ended up
  holding nothing but the domain, with `COMPOSE_PROJECT_NAME` gone — the containers, volumes and
  database kept running under a name nothing pointed at any more, and the next `start` would have
  created a second environment beside them. Both the overwrite and the stray write are fixed.

### `hm mysql -d -i dump.sql` imported nothing and reported success
- `-d` (clean `DEFINER` clauses before importing) was declared as taking an argument, so `-i` was
  read as `-d`'s argument, the file name stopped the parse, nothing was imported, and the command
  exited 0. This is the order documented in the tool's own README. Fixed, with a test pinning the
  option string and one running the documented form.

### `hm test-unit` never ran the tests
- The whole PHPUnit command line was passed to `docker compose exec` as a single argument, so
  Docker looked for a file whose name contained spaces and failed with `stat ... no such file or
  directory` — while the exit code that actually reached the caller was 0. A CI pipeline running
  `hm test-unit` was told the tests passed without one having run.

### `hm clean --json` produced one malformed entry instead of a list
- The accumulators embedded literal `\n`/`\t` inside double-quoted strings — two characters, not
  one — so `printf` (which interprets escapes) and `jq` (which does not) disagreed: every list in
  the JSON arrived as a single entry containing the whole blob, with a null reason. Fixed together
  with a second, unrelated bug it uncovered on the way: fixing the escaping by reassigning the
  output through `$(...)` strips the trailing newline, which broke the deletion loop that reads
  entries with `while read` — the last entry silently stopped being deleted.

### `hm list` and `hm clean`'s ordering depended on the machine's locale
- `sort` without `LC_ALL=C`, under `en_US.UTF-8`, ignores punctuation in its primary sort weight,
  so `magento_dev` sorted before `magento-demo` on some machines and after it on others. 1.7.0
  already fixed this in `collect_environments`; this is the same defect found independently in
  `list`'s own comparison during the Go port, and in `clean`'s own sort while porting it.

### `hm doctor`: a port conflict blamed a process called "LISTEN"
- On Linux, the port check reads `ss` and took its first column as the offending process name;
  `ss` doesn't print one there, so every conflict was reported as caused by "LISTEN". The message
  now says processes on the host, which is what can actually be checked.

### A question written to standard output could corrupt a JSON answer
- `hm docker-stop-all --yes=false ... > file` (or any non-interactive run reaching a
  confirmation) wrote its prompt to stdout before answering, so a caller reading the output as a
  document got `"Stop them all? [y/N]: "` glued onto the front of it — something `jq` refuses to
  parse. The prompt now goes to the error stream, where the rest of a command's decoration already
  goes when its answer is a document. Found while verifying the `docker-stop-all` port by hand; it
  also reached `hm clean` and `hm masquerade`.

## 🔄 Backward Compatibility

- **Nothing changes for an existing project or script that only reads text.** Every ported
  command keeps the same exit codes, the same `--json` shape, and the same questions the shell
  implementation asked.
- **`hm docker-stop-all` (and the `hm start -s` path that calls it) now answers a JSON document
  when its output is not a terminal**, the same rule every other ported command follows. A script
  that previously got nothing structured back from a piped/redirected `docker-stop-all` now gets
  one.
- **A failed `docker-stop-all` now exits reporting a Docker failure, rather than forwarding
  Docker's own exit status.** A script branching on the previous exact exit code should check it
  still means what it expects.
- **The worktree guardrail is unchanged, on purpose.** `start`, `stop`, `restart`, `down` and
  everything else that recreates or destroys an environment is still refused from a git worktree
  that has no environment registered of its own — it was briefly lost while porting those
  commands and restored before shipping (see the test-seam section above); nothing about the rule
  itself is new.
- **`hm` is now a downloaded binary that has to track the checkout.** `hm switch` and `hm update`
  fetch the matching binary for the version they move the checkout to; if that download fails, the
  installer and the switch fall back to the shell implementation rather than leaving a broken
  command.
- **`hm version` reports the exact tag distance** (`git describe --tags`, not rounded to the
  nearest one) instead of the nearest tag alone, plus a new field for which binary build is
  running — useful context to include when reporting a bug against this release.
- **`hm serve` from the brief window it existed under that name is gone**: the same command is
  `hm web` before this reaches anyone outside development.
