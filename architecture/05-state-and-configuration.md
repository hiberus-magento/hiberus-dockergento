## 5. State and Configuration Management

### 5.1 Configuration Hierarchy

The tool uses a **multi-layered** configuration system that allows per-project customization:

```
1. The tool's defaults (data/, compiled into the binary)
   ↓ Overridden by...
2. Project Configuration (config/docker/)
   ↓ Overridden by...
3. Runtime Environment Variables
```

### 5.2 Configuration Files

#### 5.2.1 The tool's defaults (`data/`)

`data/` is compiled into the binary with `go:embed` (`assets.go`); nothing is read from beside the
executable. `HM_ASSETS_DIR` points it at a checkout instead, for contributors.

**`data/properties.json`** - System default properties:
```json
{
    "MAGENTO_DIR": ".",
    "BIN_DIR": "./vendor/bin",
    "HOST_DIR": ".",
    "DOCKER_COMPOSE_FILE": "docker-compose.yml",
    "DOCKER_COMPOSE_FILE_LINUX": "docker-compose.dev.linux.yml",
    "DOCKER_COMPOSE_FILE_MAC": "docker-compose.dev.mac.yml",
    "USER_PHP": "app",
    "GROUP_PHP": "app",
    "WORKDIR_PHP": "/var/www/html",
    "COMPOSE_PROJECT_NAME": "",
    "MAIL_SERVICE": "mailhog",
    "USE_PROXY": "false",
    "TRANSFER_DB_STRUCTURE_ONLY": "@saas"
}
```

**`data/requirements.json`** - Magento → Services compatibility matrix (a bare tag is a
`hiberusmagento/<service>` image, a full reference is used as it is):
```json
{
    "2.4.7": {
        "php": "8.3-bookworm",
        "mariadb": "10.6",
        "search": "2.5-opensearch",
        "redis": "7",
        "varnish": "7.1",
        "composer": "2.7",
        "nginx": "hiberusmagento/nginx:1.18",
        "mailhog": "hiberusmagento/mailhog:1",
        "mailpit": "hiberusmagento/mailpit:1",
        "rabbitmq": "hiberusmagento/rabbitmq:3.9",
        "hitch": "hiberusmagento/hitch:1.7"
    }
}
```

**`~/.hm/config.json`** - Magento installation configuration, shared by every project. It is not in `data/`: `Engine.InstallSettings` creates it from `core.DefaultInstallSettings` the first time `install` asks for it (copying a 1.x `~/hm/data/config.json` once when there is one):
```json
{
    "language": "es_ES",
    "currency": "EUR",
    "timezone": "Europe/Madrid",
    "admin-firstname": "hiberus",
    "admin-lastname": "hiberus",
    "admin-email": "noreply@hiberus.com",
    "admin-user": "hiberus",
    "admin-password": ""
}
```
An empty `admin-password` makes `install` generate one and never write it down; one set there is respected.

**`data/local_settings.json`** - Magento configurations for development:
```json
{
    "config_set": [
        {
            "path": "web/unsecure/base_url",
            "value": "URL"  // Will be replaced by https://$DOMAIN/
        },
        {
            "path": "catalog/search/elasticsearch7_server_hostname",
            "value": "search"  // Docker service name
        },
        {
            "path": "admin/security/session_lifetime",
            "value": "31536000"  // 1 year for development
        }
    ]
}
```

**`data/command_descriptions.json`** - Command metadata (used by help system)

**`data/equivalent_versions.json`** - Mapping of equivalent versions for compatibility

**`data/default_files_magento.json`** - List of files that must be copied between host and container

**`data/table-groups.json`** - The `@groups` `TRANSFER_DB_STRUCTURE_ONLY` and `transfer-db --structure-only` accept

**`data/ai-*.json`** - Platforms, repositories and skill types of the AI tooling (`hm ai-init`, `hm ai-doctor`), and the exclusions `hm ai-context` and `hm permissions` read

#### 5.2.2 Project Configuration (`<project>/config/docker/`)

This configuration is **project-specific** and is created during `hm setup`:

**`config/docker/properties.json`** - Overrides global properties:
```json
{
    "MAGENTO_DIR": "./src",
    "COMPOSE_PROJECT_NAME": "myproject",
    "DOMAIN": "myproject.local"
}
```

**`config/docker/local_settings.json`** - Editable copy of Magento configurations
- Created by copying from `data/local_settings.json`
- Can be modified by developers for project-specific configurations

**Typical structure**:
```
project/
├── config/
│   └── docker/
│       ├── properties.json          # Project-specific properties
│       ├── local_settings.json      # Project Magento configurations
│       └── masquerade/              # Anonymization configuration
│           └── magento2/
│               └── custom.yaml
├── docker-compose.yml               # Generated by the tool
├── docker-compose.dev.mac.yml       # macOS overlay
├── docker-compose.dev.linux.yml     # Linux overlay
└── src/                             # Magento code (if MAGENTO_DIR="./src")
```

### 5.3 Configuration Loading Process

#### 5.3.1 Initialization Flow

The Go binary reads the two files itself, the project's values over the defaults (`Engine.Properties` in `dockergento/dockergento.go`, through the `fsprops` adapter). A directory with no `config/docker/properties.json` of its own is not a project. `app.Resolver` turns the properties into the project: when `COMPOSE_PROJECT_NAME` is not configured, the name is the one Docker Compose derives from the root directory (`core.DeriveProjectName`: lowercase, only `[a-z0-9_-]` kept, leading `-`/`_` trimmed); a configured name always wins.

A project-defined command (`config/hm/commands/<name>.sh`) gets the merged properties as environment variables (`projectRun.loadProperties` in `internal/cli/project_command.go`), the way the shell entry point exported them:

```bash
export MAGENTO_DIR="./src"
export COMPOSE_PROJECT_NAME="myproject"
export DOMAIN="myproject.local"
export WORKDIR_PHP="/var/www/html"
export BIN_DIR="./vendor/bin"
# etc.
```

The shell implementation also converted the pre-JSON `config/docker/properties` file into `properties.json` on every invocation. The binary converts it once, when `properties.json` is missing (see 5.9.1).

#### 5.3.2 Operating System Detection

`Platform()` in `dockergento/dockergento.go` answers `mac` or `linux` from the running OS, and the compose files are `DOCKER_COMPOSE_FILE` plus `DOCKER_COMPOSE_FILE_MAC` or `DOCKER_COMPOSE_FILE_LINUX`. A project-defined command is handed the result:

```bash
MACHINE="mac"
DOCKER_COMPOSE_FILE_MACHINE="docker-compose.dev.mac.yml"
DOCKER_COMPOSE="docker compose -f docker-compose.yml -f docker-compose.dev.mac.yml"
```

### 5.4 System State Variables

#### 5.4.1 Key Environment Variables

| Variable | Origin | Purpose | Example |
|----------|--------|---------|---------|
| `COMMAND_BIN_NAME` | the binary, for a project command | CLI command name | "hm" |
| `COMMAND_TOOLNAME` | the binary, for a project command | Full tool name | "Hiberus Dockergento" |
| `COMMAND_BIN_DIR` | the binary, for a project command | The directory above the binary's, links resolved | "~/.hm" for `~/.hm/bin/hm` |
| `COMMANDS_DIR` | the binary, for a project command | The project's commands directory | "<project>/config/hm/commands" |
| `DATA_DIR` | the binary, for a project command | The embedded `data/` extracted once, or `$HM_ASSETS_DIR/data` | "~/.hm/cache/data-<digest>" |
| `MAGENTO_DIR` | properties.json | Path to Magento code | "." or "./src" |
| `DOMAIN` | properties.json | Local domain | "myproject.local" |
| `COMPOSE_PROJECT_NAME` | properties.json, or derived from the directory | Docker project name | "myproject" |
| `MACHINE` | the binary (`Platform()`) | Operating system | "mac" or "linux" |
| `DOCKER_COMPOSE` | the binary, for a project command | Full Docker Compose command: `docker compose`, or `docker-compose` when only the standalone v1 is installed | "docker compose -f docker-compose.yml -f docker-compose.dev.mac.yml" |
| `WORKDIR_PHP` | properties.json | Working directory in container | "/var/www/html" |
| `USER_PHP` | properties.json | User in PHP container | "app" |
| `HM_OUTPUT_FORMAT` | the binary, for a project command | The output decided for this run | "text" or "json" |
| `HM_NON_INTERACTIVE` | `--yes`, or the environment | Never ask | "1" or empty |
| `USE_DEFAULT_SETTINGS` | the binary, for a project command | Set to "true" when `HM_NON_INTERACTIVE` is | "true" or unset |

#### 5.4.2 Color Variables (UI)

Handed to a project command as the escaped strings the shell held (`projectRun.palette`), empty when colour is off:
```bash
export BLUE="\033[0;34m"
export GREEN="\033[0;32m"
export RED="\033[0;31m"
export YELLOW='\033[0;33m'
export COLOR_RESET="\033[0m"
# etc.
```

The binary's own output is painted in Go (`internal/cli/palette.go` and each command's renderer), with the same colours; see 6.3.

### 5.5 Configuration Persistence

#### 5.5.1 Saving Project Properties

**Function**: `Setup.Save` in `dockergento/app/setup.go`

During `hm setup` the binary merges the decided values into `config/docker/properties.json` (creating it when missing) and keeps every other key there. `COMPOSE_PROJECT_NAME` is recorded only when it is not the name the directory would produce anyway, or when the project already had one.

**Persisted variables**:
- `MAGENTO_DIR`: Path to Magento directory
- `COMPOSE_PROJECT_NAME`: Project name (used to name containers)
- `DOMAIN`: Project's local domain

#### 5.5.2 Domain Detection from Database

**Function**: `Importer.rememberDomain` in `dockergento/app/import.go`

When the project has no `DOMAIN`, the host of `web/secure/base_url` in `core_config_data` is written to `config/docker/properties.json`, keeping the keys already there.

**Usage**: When importing a database, the tool can automatically detect the configured domain.

#### 5.5.3 Docker Compose File Generation

```
# core.RenderCompose (dockergento/core/setup.go), called by app.Setup
1. Read the requirements for the Magento version
2. Replace each <service_version> marker in docker-compose/docker-compose.template.yml
   with the service's image tag, and the mail catcher markers with the chosen one
3. Write docker-compose.yml, and the OS-specific overlays
```

**Persisted state**: docker-compose.yml files in the project

### 5.6 Dynamic Magento Configuration

#### 5.6.1 Applying Configurations

**Where**: `dockergento/app/configure.go` (applied after a database import or an installation)

```
# Executed after DB import or installation
1. Read config/docker/local_settings.json
2. Replace placeholders:
   - "URL" → "https://$DOMAIN/"
   - "DOMAIN" → "$DOMAIN"
3. Execute hm magento config:set for each entry
```

**Transformation example**:
```json
// local_settings.json
{"path": "web/unsecure/base_url", "value": "URL"}
  ↓
// Executed command
hm magento config:set web/unsecure/base_url https://myproject.local/
```

**Typical configurations applied**:
- Base URLs (http/https)
- Search hostname (Elasticsearch/OpenSearch)
- Admin security configurations (lifetime, password requirements)
- Cookie domain

#### 5.6.2 Extracting Domains from Database

**Where**: `addSelfRoutingEntries` in `dockergento/app/after_start.go`, on Linux after an environment starts

```
1. Query core_config_data for the distinct values of web/%/base_url
2. Keep the host of every value that is a URL (scheme and path dropped)
3. Write each host into the php container's /etc/hosts, pointing at the TLS terminator,
   so the store can call itself by its own domain
```

**Usage**: only the self-routing entries of the php container.

### 5.7 Docker Services State

#### 5.7.1 State Validation

The tool **does not keep its own record of containers**: it asks Docker. A use case that needs a
service looks its container up through the Docker API by its labels — `hm.project` (or
`com.docker.compose.project` when that is absent) and `com.docker.compose.service`, see
[environment labels](../docs/environment-labels.md) — in `resolveContainer`
(`dockergento/app/container.go`), and refuses with `service_not_running`
(exit 5) and the hint `hm start <service>` when it is not running.

**Advantage**: No desynchronization between real state and assumed state.

#### 5.7.2 No Automatic Service Startup

A command that needs a stopped service does not start it behind the user's back: it refuses with
exit 5 and says which `hm start` to run. Starting an environment can repoint bind mounts or take
ports another project holds, so it stays an explicit decision.

### 5.8 Tool-Specific Configuration

#### 5.8.1 xDebug

**Owner**: the Go binary. `hm debug-on` is `internal/cli`'s `debugOn`, and the host is resolved by
`dockergento/adapters/machine/xdebug_host.go`.

> **This section was wrong in every particular until 2026-09-13**, and the correction is recorded
> rather than quietly applied. It described a macOS default of `host.docker.internal`, a Linux
> lookup of the **default gateway**, and activation by renaming a `.ini.disabled` file. None of
> those was ever implemented — not by the shell, not by the Go port. Nothing enforces this document,
> which is how it stayed wrong across three cycles while reading as authoritative.

**Host resolution** — the address xdebug inside the container calls back to reach the IDE:

| Platform | Answer | Why |
|---|---|---|
| macOS | **not applicable** — empty, and no patch is made | the IDE is reachable without one; the handler skips the host edit entirely |
| WSL2 | `host.docker.internal` | matched on `microsoft-standard` in `/proc/version` |
| WSL1 | `10.0.75.1` | matched on `Microsoft` in `/proc/version` |
| Other Linux | `docker0`'s own **inet** address | `ip addr show docker0`, falling back to `ifconfig docker0` |
| Linux, unresolvable | **a failure**, exit non-zero | `ErrNoBridgeAddress` |

Three details are load-bearing and easy to get wrong when reading the code quickly:

- **`microsoft-standard` is tested before `Microsoft`**, inverting the shell's original order. A WSL2
  kernel string can carry a capital-M `Microsoft` token in a build-host field; checking the more
  specific token first is what stops it being misdetected as WSL1 and handed the wrong address.
- **The `docker0` lookup excludes `inet6`.** Both share the `inet` prefix and name different address
  families. Real `ip` output lists `inet` before `inet6`, so a parser that matched both would
  usually return the right address anyway — by ordering, not by correctness.
- **"Not applicable" and "applicable but unresolved" are distinct answers.** macOS is `("", nil)`;
  a Linux box whose bridge cannot be found is `("", ErrNoBridgeAddress)` and refuses. Collapsing
  them would make a normal Mac indistinguishable from a broken Linux machine.

**Activation / deactivation** — a `sed` on the extension's ini, not a rename:

```bash
# hm debug-on  — uncomment the extension, patch the host if one resolved, restart phpfpm
sed -i -e 's/^;zend_extension/zend_extension/g' /usr/local/etc/php/conf.d/docker-php-ext-xdebug.ini

# hm debug-off — comment it back out, restart phpfpm
sed -i -e 's/^zend_extension/;zend_extension/g' /usr/local/etc/php/conf.d/docker-php-ext-xdebug.ini
```

The host patch, when a host resolved, targets a **different file** — `xdebug.ini`, not
`docker-php-ext-xdebug.ini` — and rewrites `xdebug.remote_host` (v2) and `xdebug.client_host` (v3).

After the restart, `debug-on` reads back `php -v` for the Xdebug version and `php -i` for the
relevant settings, whose key names differ between v2 (`remote_*`) and v3 (`client_*`). If Xdebug is
not installed at all, it says so and exits **0** — the edits and the restart already succeeded, so
there is nothing to report as failure.

#### 5.8.2 Masquerade (Anonymization)

**Configuration**: `config/docker/masquerade/magento2/*.yaml`

- Priority: Project custom configuration
- Fallback: Default configuration in Docker images

**Execution** (`Importer.Anonymise` in `dockergento/app/anonymise.go`): the
`hiberusmagento/masquerade` image runs as a one-off container on the database's network (not as a
service of the project), with the database credentials read from the db container and, when the
project has `config/docker/masquerade`, those rules mounted at `/app/masquerade` and passed as
`--config`.

#### 5.8.3 SSL Certificates

**Management**: `hm ssl [domain]` (`Operator.InstallCertificate` in `dockergento/app/certificate.go`)

```
1. Refused from a git worktree with no environment of its own (the terminator is the main one's)
2. mkcert is installed when missing (Homebrew on macOS, the release binary on Linux)
3. A certificate for the domain, localhost, 127.0.0.1, 0.0.0.0 and ::1 is generated in a
   temporary directory, signed by mkcert's local authority
4. The pem is copied into the hitch container at /etc/hitch/testcert.pem and given to hitch
5. hitch is restarted
```

**Storage**: nothing is kept in the project; the certificate lives in the hitch container.

### 5.9 Migration and Compatibility

#### 5.9.1 Old Format Refactoring

Before 2.0 every invocation converted the old `config/docker/properties` (`KEY=value` lines) into
`config/docker/properties.json`, and deleted the old file. The binary's properties reader
(`dockergento/adapters/fsprops`, which every command loads through) converts it **once**: only
when `properties.json` does not exist, so a project that has both is read exactly as before.

- Blank lines and `#` comments are skipped, leading spaces trimmed, the key is what comes before
  the first `=` and the value is the rest (it may contain more `=`), with double quotes removed.
- `properties.json` is written beside it and moved into place.
- The old file is kept, never deleted: renamed `properties.bak`, or the first free
  `properties.bak.N` when that name is taken, so an earlier backup is never overwritten.
- The conversion is announced on stderr; stdout (and a `--json` document) is untouched.

A directory with no old file gets nothing written into it.
