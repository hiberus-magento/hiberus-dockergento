# Dockergento 2.0 — decisiones de arquitectura

> Punto de partida para la implementación. Recoge las decisiones cerradas, lo que se ha
> verificado contra el código de la 1.7.0, y el orden en el que se va a construir.
>
> Documento vivo: cada decisión que se revise se edita aquí, no se añade una nota al final.

---

## 1. El problema

Dockergento resuelve hoy «un desarrollador, un proyecto, un stack». Lo que hay que habilitar es
«N agentes, un proyecto, N ramas a la vez», y el modelo actual falla en tres ejes:

- **Recursos.** N stacks completos (MariaDB + OpenSearch + RabbitMQ + Redis + Varnish) no caben
  en un portátil. Ocho worktrees son del orden de 30 GB de RAM.
- **Colisiones.** Puertos, nombres de contenedor, proyectos de compose, bases de datos.
- **Tiempo de provisión.** `setup:install` son 3-6 minutos por worktree. Inaceptable como coste
  de arranque de cada tarea de un agente.

El modelo elegido es **servicios de estado compartidos con aislamiento lógico, y por worktree
únicamente el runtime de aplicación**.

## 2. Qué se lleva ya construido

La 1.7.0 no es el punto de partida de una reescritura: es la **especificación ejecutable** de casi
todas las decisiones de abajo, validada por 1.169 aserciones y con el razonamiento de cada una en
`openspec/changes/archive/`.

| Decisión de 2.0 | Ya existe en 1.x | Dónde |
|---|---|---|
| Enrutado por dominio, sin aritmética de puertos | `hm proxy` (Traefik) + certificado comodín | NET-01/02 |
| Provisión rápida de base de datos | `hm db freeze` / `clone` (copia de volumen) | DB-02 |
| Sólo runtime por worktree | perfiles `lite` / `agent` / `full` | WT-02 |
| Registro de worktrees fuera del checkout | `~/.hm/worktrees/<proyecto>/<nombre>.json` | WT-02 |
| Contrato para agentes | `--json`, códigos de salida 0-6, errores estructurados | CLI-01 |
| Herramientas tipadas para agentes | `hm mcp` (lectura y escritura acotada) | AI-03/04 |
| Permisos derivados, no escritos a mano | `hm permissions` sobre la clasificación de riesgo | AI-02 |
| Contexto del proyecto para agentes | `hm ai-context` (AGENTS.md, .mcp.json) | AI-05/06 |
| Recolección de huérfanos | `hm clean` (entornos, volúmenes, worktrees) | ENV-03/WT-03 |

Esto cambia la naturaleza del trabajo: no es diseñar 2.0, es **portarla con una implementación de
referencia y una batería de pruebas de aceptación ya escritas**.

## 3. Hallazgos verificados sobre la 1.7.0

Comprobados contra el código, no heredados de un informe. Se corrigen aquí las tres afirmaciones
que no se sostenían.

### 3.1 Un worktree lee las properties del checkout padre — **confirmado, y grave**

`bin/run` fija `CUSTOM_PROPERTIES_DIR` a partir de `HM_ROOT` (línea 49), carga las properties
(línea 58) y **sólo después** reasigna `HM_ROOT` al worktree (línea 120). La consecuencia que el
informe original no nombraba: `save_properties` desde un worktree registrado **escribe en el
checkout padre**, y `hm setup -f` —permitido en worktrees registrados— regenera properties del
padre y compose del worktree. No es una lectura incorrecta, es corrupción de estado ajeno.

### 3.2 `vendor/` enlazado rompe el registro de módulos — **confirmado con PHP real**

Reproducida la estructura que genera Composer y ejecutada en las dos topologías:

```
symlink:     psr-4 Vendor\ -> <principal>/app/code/Vendor
             autoload files -> <principal>/app/etc/NonComposerComponentRegistration.php
             módulos registrados: los del checkout principal

bind mount:  psr-4 Vendor\ -> <worktree>/app/code/Vendor
             módulos registrados: los del worktree
```

`$baseDir` sale de `dirname($vendorDir)`, y PHP resuelve `__DIR__` al destino real del enlace. No
es sólo que el autoloader apunte al sitio equivocado: `autoload_files.php` carga
`NonComposerComponentRegistration.php` desde `$baseDir`, y ese fichero busca los `registration.php`
en *su* directorio. **Los módulos del worktree no se registran nunca.** Un agente editaría su rama
sin ver ningún efecto.

Afecta sólo a Linux; en macOS se copia el volumen de código, que es la solución correcta.
**Acción inmediata sobre la 1.7.0**, ver §8.

### 3.3 Concurrencia: no hay ninguna — **confirmado**

Cero `flock` en el repositorio. Y encima:

- `hm_worktree_save` escribe el registro con redirección directa, sin renombrado atómico.
- Alta de worktree: comprobar registro → crear worktree → escribir overlay → escribir registro,
  sin exclusión mutua entre medias.
- Cuatro temporales de nombre fijo: `agent_context.sh:139,168` y `anonymisation.sh:52,64`.
- `rmdir` del directorio compartido del registro sin lock.

Es el mismo defecto cuatro veces: bash no tiene dónde poner estado compartido.

### 3.4 Correcciones al informe de partida

- **`hm.agent` está vacía, pero el check de anonimización sí funciona.** `HM_AGENT` no se asigna
  en ningún sitio, así que la etiqueta del contenedor es inútil y no se puede preguntar «qué
  entornos son de agentes». Pero `doctor/98-anonymised.sh` se activa por `HM_PROFILE == agent`,
  que sí se exporta. El daño es menor y distinto del que se le atribuía.
- **El suelo de arranque ya no son 580 ms: son ~147 ms** (`hm --version`), y ~230 ms un comando
  que habla con Docker. El 580 vive en un comentario del test de presupuesto y está obsoleto. El
  rendimiento de arranque **no es un argumento válido** para migrar a Go.
- **La versión del protocolo MCP** que negocia la 1.7.0 es `2025-06-18`, con `2025-03-26` y
  `2024-11-05` como alternativas conocidas. Que exista una revisión posterior no se ha podido
  verificar desde aquí; en cualquier caso el comportamiento es correcto —se contesta en la versión
  del cliente cuando se conoce— y actualizar la lista es una línea.

## 4. Decisiones

### ADR-001 — El CLI se reescribe en Go

**Decisión.** El punto de entrada pasa a ser un binario Go que delega en bash lo no migrado.

**Motivos, por orden de peso real:**

1. **Concurrencia con cancelación.** Levantar N worktrees en paralelo y poder abortar limpio no se
   hace en bash.
2. **Estado compartido con transacciones.** Todos los defectos de §3.3 son el mismo, y no tienen
   arreglo bueno en bash.
3. **Testabilidad de lo que hoy no se prueba.** La suite prueba bien lo determinista; la
   concurrencia y las máquinas de estado no las prueba, y son justo el núcleo de 2.0.
4. **API del daemon en lugar de parsear stdout** del CLI de compose.

**Lo que no es un motivo:** el arranque (§3.4). Se cita a menudo y está medido en contra.

**Descartados:** PHP (sin binario, sin concurrencia real), Python (empaquetado), Node/TS (peso y
arranque), Rust (el cuello de botella es la E/S del daemon, no nuestro código).

**Stack:** `docker/docker/client`, `compose-spec/compose-go/v2`, `spf13/cobra`+`viper`,
`charmbracelet/bubbletea`, `golang.org/x/sync/errgroup`, SQLite sin cgo (`modernc.org/sqlite`).

**Aviso:** el tipo `Worktree` de `go-git` **no** es `git worktree`. Para worktrees se usa
`exec.Command("git", "worktree", ...)`. Es la excepción razonable a «nada de shell-out».

**Condición no negociable:** CI que compile y pase los tests en cada push, desde el primer commit.
Con bash, un commit malo rompe a quien ejecuta ese comando; con un binario, un build roto deja sin
herramienta a todo el que haga `pull`.

### ADR-002 — Servicios compartidos con aislamiento lógico

Un solo daemon por servicio de estado. Magento soporta nativamente los cuatro mecanismos:

| Servicio | Aislamiento | Flag / clave |
|---|---|---|
| MariaDB | un schema por worktree | `--db-name=m2_<wt>` |
| OpenSearch | un prefijo de índice | `--opensearch-index-prefix=<wt>` |
| Valkey/Redis | una DB numérica por propósito | `--cache-backend-redis-db`, `--page-cache-redis-db`, `--session-save-redis-db` |
| RabbitMQ | un vhost | `--amqp-virtualhost=<wt>` |
| Traefik / Mailpit | compartidos, sin aislamiento | etiquetas de Docker |

Por worktree se levanta **sólo nginx + php-fpm**. Varnish, cron y consumers apagados por defecto,
activables por flag en el worktree que los esté probando.

**Consumo estimado:** base compartida ~3,8 GB; cada worktree ~40 MB en reposo y ~700 MB activo.
Ocho worktrees con dos trabajando ≈ 5,5 GB frente a ~30 GB de ocho stacks completos.

**Cuándo romper el modelo:** stack propio sólo si el agente toca versión de PHP, versión del motor
de búsqueda o configuración del engine de base de datos. Un cambio de schema **no** lo justifica:
cada worktree tiene el suyo.

**Lo que se compra y lo que se paga.** Compartir servidor obliga a provisionar por SQL: el datadir
pertenece al servidor y copiar el directorio de un schema dentro de un servidor vivo no registra
nada (InnoDB no se entera; habría que hacer `DISCARD`/`IMPORT TABLESPACE` tabla por tabla, 700
veces). Es decir, **los servicios compartidos cuestan la copia rápida de volumen que hace hoy
`hm db clone`**. Es un intercambio aceptable y hay que escribirlo como tal.

**Radio de daño.** Un servicio compartido es un fallo compartido: la consulta desbocada de un
agente ahoga a los demás, y un servicio corrupto tumba los N worktrees. Los límites de `cpus` y
`memory` por worktree **no protegen de esto**. Hace falta, y es trabajo explícito:
`max_user_connections` por usuario de schema, `max_execution_time` en MariaDB, y cuota de heap en
OpenSearch.

### ADR-003 — Provisión por clon de un schema base

Nada de `setup:install` por worktree. Se instala y sanea **una vez** un `m2_base`, se vuelca a
disco, y cada worktree se siembra de ese volcado al crearse y se destruye al eliminarlo.

```bash
# una vez, tras instalar y sanear m2_base
mysqldump --single-transaction --no-tablespaces m2_base > /seed/m2_base.sql

# al crear el worktree
mysql -e "CREATE DATABASE m2_${WT}"
mysql m2_${WT} < /seed/m2_base.sql

# al destruirlo
mysql -e "DROP DATABASE m2_${WT}"
```

Con un volcado saneado de ~300 MB: 20-40 s frente a 3-6 min. El coste dominante es el DDL de las
~700 tablas, no los datos.

**Un schema por worktree, creado al alta y borrado al baja.** Se descartó un pool caliente de
schemas preprovisionados: es más rápido pero introduce estado que no pertenece a nadie. Se
reconsidera si `wt add` supera los ~45 s con el seed ya adelgazado, o si se mide que los agentes
crean y destruyen entornos varias veces por hora.

**Tuning del contenedor de MariaDB (sólo desarrollo, jamás producción):**

```ini
innodb_flush_log_at_trx_commit = 2
sync_binlog = 0
skip-log-bin
```

**Saneado del seed.** La palanca real es el tamaño: fuera `sales_*`, fuera `*_log`, catálogo
recortado. De 8 GB a 300 MB baja el import de minutos a segundos. Para la anonimización se
reutiliza la imagen `hiberusmagento/masquerade`, que ya se mantiene.

**Un seed por versión.** El fingerprint no puede ser sólo el hash de `composer.lock`: dos ramas en
versiones distintas de Magento o de PHP no comparten seed. El fingerprint es
`composer.lock` + versión de Magento + versión de PHP, y para detectar deriva de schema, las filas
de `setup_module` (que es lo que compara `setup:upgrade`).

**Parcheo obligatorio tras clonar**, o el worktree arranca roto:

```sql
UPDATE core_config_data SET value='https://${WT}.m2.test/'
  WHERE path IN ('web/unsecure/base_url','web/secure/base_url');
```

Y en el `env.php` del worktree, **el mismo `crypt/key` que la base**: si cambia, todos los valores
cifrados de `core_config_data` quedan ilegibles.

**Escape documentado:** un `mysqld` por worktree con el datadir horneado en imagen (CoW). Arranque
~3 s y disco sólo el delta, a cambio de ~200 MB de RAM por instancia. En Linux con XFS/btrfs hay
variante nativa (`cp --reflink=always`, `btrfs subvolume snapshot`), no portable a macOS.
Reconsiderar si se pasa habitualmente de 6-8 worktrees simultáneos.

### ADR-004 — `vendor/` se monta; nunca se enlaza ni se copia

**Verificado experimentalmente (§3.2).** El requisito no es que `vendor` sea un directorio real en
el host: es que lo sea **dentro del contenedor**, que es donde corre PHP. Un montaje lo consigue;
un enlace no. Y copiarlo son 1-2 GB y decenas de miles de ficheros por worktree, que en Magento 2
no es aceptable.

En Linux, montaje bind del `vendor` del principal sobre `/var/www/html/vendor`. En macOS, donde el
código vive en un volumen, Docker 26+ permite montar **un subdirectorio de un volumen**
(`volume.subpath`, comprobado con compose real sobre el daemon 27.4): el worktree monta `vendor`
del volumen del entorno principal y copia sólo el código. Reduce la copia de arranque de ~695 MB a
las decenas de megas del código.

Se comparte **sólo mientras las dependencias sean las mismas** —se compara `composer.lock`— y
**siempre en sólo lectura**: es lo que impide que un `composer require` en una rama corrompa lo que
están leyendo el principal y otros cinco worktrees. La decisión se guarda en el registro del
worktree, no se recalcula.

En la 1.7.1 ya está la parte de Linux; el `subpath` de macOS es trabajo de 2.0. Dos ramas con el
mismo `composer.lock` comparten, indexadas por hash del lock.

Complementos:
- `COMPOSER_HOME` compartido (caché y `auth.json` con las claves de Adobe Commerce).
- Alternativa en Linux con XFS/btrfs: `cp --reflink=always -r`.
- **Descartado:** `cp -al` (enlaces duros). Rápido, pero un parche de Composer sobre `vendor` muta
  el original y contamina todos los worktrees.

### ADR-005 — php-fpm en modo `ondemand`

Es el mayor ahorro individual de memoria.

```ini
pm = ondemand
pm.max_children = 5
pm.process_idle_timeout = 10s
opcache.memory_consumption = 128
opcache.jit = disable
```

Con `static`/`dynamic`, FPM mantiene hijos vivos siempre, y cada hijo de Magento ocupa 80-150 MB
aunque nadie visite el sitio. Con `ondemand` hay cero hijos en reposo (sólo el maestro, ~15 MB).

**El detalle que lo hace viable:** opcache vive en memoria compartida colgada del maestro, así que
matar hijos no la vacía y el hijo nuevo arranca con el bytecode compilado.

**Precisión honesta:** los ~100-300 ms de coste tras el reposo son el fork con opcache caliente.
La primera petición de un worktree en modo `developer` con `generated/` frío son 30-60 s. No
invalida la decisión, pero hay que decirlo o el equipo lo medirá y pensará que el número era falso.

**Además:** modo `developer`, sin `di:compile` ni `static:deploy`; `generated/` y `pub/static` se
materializan bajo demanda. Xdebug apagado por defecto y activable por worktree — con N worktrees,
encendido en todos es la diferencia entre usable e inusable.

**Dimensionado pendiente:** `pm.max_children` × N worktrees contra `max_connections` de la MariaDB
compartida.

### ADR-006 — Dos topologías, no una

2.0 tiene que servir igual de bien al proyecto de cliente que no cabe en el modelo compartido
—versión distinta de Magento, motor de búsqueda distinto, stack propio— y al trabajo con agentes.

- **`classic`**: un stack por proyecto. Es lo que hace la 1.x y donde vive hoy todo el equipo.
- **`orchestrated`**: servicios compartidos y N worktrees.

La topología es un atributo del proyecto (`properties.json`), no del binario, y **el registro tiene
que modelar las dos desde el primer día**. Retrofitear esto obliga a migrar el estado de todo el
mundo.

Consecuencia de orden: el núcleo Go alcanza paridad en el modo clásico **antes** de construir el
orquestado. Así el equipo entero gana pronto y lo arriesgado es aditivo.

### ADR-007 — Arquitectura hexagonal en el núcleo

El núcleo no sabe que existe una CLI. La CLI, MCP y —más adelante— la web de visualización son
adaptadores de entrada sobre los mismos casos de uso.

```
internal/core/         dominio: Project, Worktree, Service, Seed, State
                       cero imports de docker, git, cobra o de impresión
internal/core/ports/   interfaces: ContainerEngine, VCS, Registry, ComposeRenderer, Clock, FS
internal/app/          casos de uso: CreateWorktree, Reconcile, ProvisionSchema, Collect
internal/adapters/     docker (SDK), git (exec), registry (sqlite), compose (compose-go), fs
cmd/hm/                adaptador de entrada: CLI (cobra)
internal/api/          adaptador de entrada: HTTP (web app)
internal/mcp/          adaptador de entrada: MCP
```

Dos reglas que son las que se incumplen siempre y sin las cuales esto no sirve de nada:

- **El núcleo no imprime.** Devuelve datos y errores tipados; lo que se ve lo decide el adaptador.
  Es lo que hace que texto, `--json`, MCP y HTTP salgan de la misma lógica sin duplicarla.
- **El núcleo no sabe la hora ni dónde está el disco.** `Clock` y `FS` como puertos. Suena a
  ceremonia hasta que se comprueba que la reconciliación y el GC se prueban **sin Docker**, en
  milisegundos. Hoy media suite necesita Docker y tarda 25 minutos: eso es lo que compra el
  hexágono, más que la web.

**Go aburrido dentro del hexágono:** structs e interfaces normales, sin genéricos gimnásticos, sin
reflexión, sin frameworks de inyección, sin canales donde vale un bucle. Estructura sí, ingenio no.

**Sin demonio en 2.0.** La web lee la misma SQLite y se suscribe a los eventos de Docker por su
cuenta. Un `hmd` es otra cosa que mantener viva, reiniciar y depurar; si hace falta, se añade
después sin tocar el núcleo.

### ADR-008 — 1.x en bash, 2.x en Go, un solo binario instalado

- **1.x pasa a mantenimiento**: sólo corrección de fallos. Si se siguen añadiendo funcionalidades
  en bash se pagan dos veces y la migración no termina nunca.
- **Un único `hm` instalado.** El binario Go *es* `hm` y localiza el árbol bash al que delega. Dos
  instalaciones separadas significan gente ejecutando la que no era y reportando fallos contra la
  versión equivocada.
- **Mismo repositorio**, `main` moviéndose a Go y `release/1.x` como rama de mantenimiento. El
  archivo de OpenSpec, `docs/research/` y los tests son el mapa con el que se porta; separarlos es
  tirarlo.
- **El bash es infraestructura permanente, no andamiaje.** `bin/run` ya carga comandos propios del
  proyecto desde `config/hm/commands/` con su propio `command_descriptions.json`. Eso es una
  capacidad del producto y los comandos de proyecto van a ser bash siempre.
- **Cada comando migrado se valida contra el bash** con los mismos tests de integración.

**Reparto del backlog.** Con 1.x en mantenimiento, la Ola 6 casi entera (ENV-04 a ENV-10, UI-01 a
UI-04, INST-03) es 2.0 por naturaleza. En 1.x sólo quedan los defectos de §3 y lo que aparezca en
la beta.

## 5. Tandas de migración

Escalonadas por frecuencia de uso y riesgo, no por completitud. Casi todo se beneficia: incluso un
passthrough como `hm magento cache:flush` paga hoy ~200-400 ms de bash + CLI de compose antes de
que Magento vea el comando, y se ejecuta decenas de veces al día.

| Tanda | Comandos | Por qué |
|---|---|---|
| 1 | `start stop restart logs exec describe list doctor magento composer` | El 90 % de las invocaciones diarias |
| 2 | `db worktree proxy clean setup down` | Los que tocan estado: registro y locking |
| 3 | El resto de `environment`, `database`, `files` | Rutina |
| 4 | `cloud-* transfer-* grunt ssl compatibility ai-*` | Orquestan herramientas externas y se usan poco; pueden quedarse en bash |

## 6. Puntos abiertos, con criterio de decisión

| # | Punto | Cómo se decide |
|---|---|---|
| 1 | Deriva de schema del seed | Fingerprint (§ADR-003) + `setup:upgrade` sólo con el delta al crear. `seed rebuild` cuando el delta deja de ser barato; decidir si se automatiza por umbral |
| 2 | Registro y slots | SQLite con una entidad por fila. Slots `0..N` reutilizables; `databases` de Valkey por encima de 16 (con 128 y 3 DB por worktree salen ~42) |
| 3 | GC de huérfanos | Barrido al arrancar + comando explícito. Sin esto el modelo se degrada en días |
| 4 | Sincronización en macOS | **Es la Fase 1.** Cuántas sesiones aguanta un portátil del equipo puede ser un techo más bajo que el de RAM |
| 5 | Límites por worktree | `cpus` y `memory` en el compose del worktree, más las cuotas de §ADR-002 en los servicios compartidos |
| 6 | Observabilidad | `status` agregado (bubbletea), logs por worktree, detección de zombis (contenedor arriba, aplicación caída) |
| 7 | MCP con varios worktrees | Un servidor que direccione cualquier worktree desde el registro, en lugar de N registros con `cwd` fijo |

---

## 7. Fase 1: la puerta de decisión

Antes de escribir una línea de Go. Ninguno de estos cuatro números necesita el binario, y los
cuatro pueden cambiar la arquitectura:

1. **Sincronización en macOS.** Cuántas sesiones simultáneas aguanta un portátil del equipo antes
   de degradarse. Si el techo son tres, el resto del modelo da igual.
2. **Tiempo real del seed** sobre un proyecto de cliente, no sobre un Magento limpio.
3. **Abanico de versiones** de Magento y PHP en los proyectos vivos: dice cuántos seeds hacen falta
   y cuántos proyectos no caben en el modelo compartido.
4. **Diez worktrees a la vez con el bash actual**, tras los arreglos de §8. Dice si se migra con
   calma o con prisa.

Validación previa, a mano y sin Go: stack compartido levantado con un compose plano, dos worktrees
sembrados desde seed, comprobando que conviven sin colisiones.

## 8. Fases

```
0    Cerrar la 1.7.0 con el equipo
     · P0 en bash: properties del worktree (§3.1), HM_AGENT, atomicidad de los cuatro
       temporales, flock en ~/.hm, validación de colisiones de nombre y dominio
     · [hecho, 1.7.1] Montar vendor en lugar de enlazarlo (§3.2)
1    Validar el modelo sin Go — los cuatro números de §7
     ── PUERTA DE DECISIÓN ──
2    Esqueleto: núcleo + puertos, adaptador CLI, puente a bash. El equipo no nota nada
3    Adaptador Docker (SDK) + tanda 1           ← aquí gana todo el equipo
4    Registro SQLite con las dos topologías + tanda 2
5    Servicios compartidos, seed, worktrees, GC ← aquí gana el trabajo con agentes
6    Adaptadores de agente: --json, MCP, HTTP para la web
7    Tanda 3; la 4 se queda en bash mientras compense
```

**Distribución:** goreleaser, binarios para darwin/arm64, darwin/amd64, linux/amd64, linux/arm64.
Instalación por `curl` y, si compensa, tap de Homebrew.

**Imágenes:** se reutilizan `hiberusmagento/*`. Hay que auditar qué versiones siguen vivas y si la
de php necesita ajustes para `ondemand` y para Xdebug conmutable en caliente.

## 9. Lo que no se hace

- **No se reescriben los 63 comandos.** Se migran por tandas y la cola larga puede quedarse en
  bash indefinidamente.
- **No hay demonio** en 2.0.
- **No se rompe el modo clásico.** Un proyecto que hoy funciona tiene que seguir funcionando igual
  después de instalar el binario.
- **No se toca la 1.x** salvo corrección de fallos.
